# Forge Agent 全面复查与改进路线

> 这是修复前的历史审查基线。后续实施与验证见 [2026-10-29 框架升级记录](framework-repo-map-upgrade-2026-10-29.md)。

审查日期：2026-10-28。代码基线：`dev`，`56c3a55`。本报告针对当前代码，结合 `forge部分/study/agent-hybrid-analysis.md` 理解设计目标。

本轮进行源码审查、全量回归和临时仓库复现，没有修复业务代码，没有调用付费模型，没有提交或推送代码。文档中的建议尚未实施。

## 1. 结论与证据边界

ReAct 主循环、Repo-map、模型适配层、Runtime 和事件日志的职责划分可以保留。当前最需要改进的是工具执行契约、任务权限、失败产物保存、成本统计和真实环境验证。继续增加 Agent 数量或只更换模型，都不能消除这些确定性的工程问题。

本轮发现 12 项问题：8 项高优先级问题和 4 项其他问题。其中 11 项有行为复现；GitHub 凭据问题确认了含伪密钥的 URL 构造，未检查真实凭据或证明已发生泄漏。严重程度表示建议修复顺序，不代表已发生生产事故。

- Windows 全量测试：**468 passed，4 skipped，142.43 秒**。日志：`logs/comprehensive-audit-tests.txt`。
- 额外验证使用临时仓库、MockBackend、录制 Runtime，以及真实 Linux Docker；没有修改用户仓库中的业务文件。
- 测试全部通过与下列缺陷同时存在，说明现有覆盖还缺少部分平台、失败出口和跨入口契约。
- 30 题 Flash/Pro A/B 仍未完成。已有真实微型任务和单题 gold 验证可以证明部分链路可用，无法据此判断模型能力差异。

## 2. 已确认的问题

### R01 · P1：Windows 宿主机上的 Docker 文件工具无法处理正常大小的内容

位置：[tools/file_tool.py](../tools/file_tool.py#L35)、[tools/runtime.py](../tools/runtime.py#L290)。

文件操作把辅助模块源码与全部参数一起编码进 `python -c`，再作为 Docker 命令行参数传入。Windows 创建进程有命令行长度限制；把执行环境统一成 Linux 容器，并没有消除 Windows 宿主机的限制。

实际复现：通过 Docker `file_write` 新建一个含 25,000 个 ASCII 字符的文件，返回 `WinError 206`，文件未创建。该内容低于现有 32,000 字节的大文件覆盖阈值，而且是新文件。`file_edit` 的 old/new 内容与较大的补丁也经过类似传输路径。

建议：增加 Runtime 的参数数组和标准输入接口。脚本与数据通过 stdin 或临时文件传输；Docker 使用 `exec -i` 或复制文件。不要继续把完整业务数据拼进命令行。

验收：Windows → Linux Docker 的真实读写、精确编辑和补丁应用覆盖 25 KB、100 KB、多字节字符与多行内容；断言实际内容正确，不能只模拟 subprocess。

### R02 · P1：结构化 Git 工具把参数当作 Shell 代码执行

位置：[tools/git_tool.py](../tools/git_tool.py#L29)。

`_run_git` 将参数拼成字符串，只对含空格的参数加双引号。Bash 的双引号仍允许命令替换，普通参数也可能包含 Shell 运算符。

实际 Docker 复现：将提交说明设为 `Fix $(touch audit-marker.txt)`，Git 提交成功，但额外创建了 marker 文件，提交说明也变成 `Fix`。这里的文件创建发生在临时仓库容器中；没有证据表明发生宿主机逃逸。

建议：Git 工具使用 `exec_argv(["git", ...])`；提交说明和文件路径始终作为数据传递。路径参数适当使用 `--`，防止被解析为 Git 选项。单纯增加双引号不够。

验收：含空格、单/双引号、`$()`、分号、换行与前导 `-` 的说明和路径，要么准确处理，要么明确拒绝；不能产生额外命令副作用。

### R03 · P1：主任务的 read_only 只是提示，执行层仍允许修改

位置：[agent/core.py](../agent/core.py#L586)、[entry/cli.py](../entry/cli.py#L119)。

`task_type=read_only` 增加了提示，并跳过修改类完成门禁，但主任务注册表仍包含 `file_write`、`file_edit`、`apply_patch`、Shell 和提交工具。

实际复现：使用生产 `_build_registry` 和 Docker，向只读任务提供 `file_edit → finish` 的录制模型响应，任务返回 success，文件确实被修改。

这里需要区分：现有 explore/review 子 Agent 已按工具白名单过滤；本项指主任务 `read_only` 的执行路径。

建议：为任务建立执行能力集合，注册表展示与执行器校验同时生效。子任务只能继承或收窄父任务能力。需要运行会生成缓存的测试时，采用一次性工作区，并明确“允许执行测试”与“允许修改用户源码”的区别。

验收：即使模型主动调用写工具、Shell 或 fork，也无法修改原仓库；拒绝原因写入 Observation。

### R04 · P1：确认机制在不同工具之间不一致，并可被命令前缀绕过

位置：[entry/cli.py](../entry/cli.py#L119)、[tools/test_tool.py](../tools/test_tool.py#L111)、[tools/shell_tool.py](../tools/shell_tool.py#L220)。

确认回调仅传给 ShellTool；`test.command` 可以直接执行任意命令，Git 提交工具也不经过同一确认机制。Shell 的只读判断按字符串前缀处理，不能正确识别复合命令。

复现一：注册一个始终拒绝的确认回调，通过 `test.command` 执行写入 marker 的命令，执行成功，确认回调调用次数为 0。

复现二：`echo harmless && git commit -m audit` 被判定为 readonly，`needs_confirmation=False`。只进行了策略函数检查，没有执行该复合命令。

建议：把命令权限与确认决策放到公共 ToolExecutor/命令执行服务，Shell、测试、Git 使用同一规则。结构化工具尽量使用参数数组；复杂 Shell 不应因首个命令看似只读就自动获准。明确 `--confirm` 的覆盖范围，并与文档一致。

验收：同一受控操作经由 Shell、test.command、Git 工具执行时，权限结果一致；复合命令和解释器调用不能继承简单只读前缀的权限。

### R05 · P1：失败 fork 子任务的修改会被清理，父任务无法恢复

位置：[agent/core.py](../agent/core.py#L479)、[multi_agent/sub_agent.py](../multi_agent/sub_agent.py#L272)、[tools/task_tool.py](../tools/task_tool.py#L261)。

成功出口保存 patch，但 max_steps、give_up 等失败出口没有保存相同产物。SubAgent 的 finally 随后清理隔离 worktree；失败结果格式化也没有补丁交付通道。

实际复现：fork 子任务在唯一一步内成功编辑文件，随后达到 max_steps；结果为 `max_steps`，`patch=None`，隔离 worktree 已不存在，父工作区保持原状。隔离有效，但有效的中间修改丢失。

建议：所有终止状态都先固化产物，再清理运行资源。产物至少包括 base commit、partial patch、修改文件、测试结果、停止原因与日志位置。失败补丁标记为待审查，不自动应用。保存失败时保留可恢复的工作区。

验收：成功、预算耗尽、超时、主动停止、模型错误与异常出口都有可追溯产物；父任务可以检查并选择复用失败子任务的部分成果。

### R06 · P1：父任务统计不包含子 Agent 消耗，预算无法约束整次运行

位置：[agent/core.py](../agent/core.py#L301)、[agent/core.py](../agent/core.py#L495)、[tools/task_tool.py](../tools/task_tool.py#L204)。

父任务只累加自身模型响应的 Token。子任务通知里的 Token 被写进文字，没有计入父任务 `total_tokens`；子任务另有固定 40,000 Token 预算。

录制复现：父预算为 500，注入一个已消耗 6,000 Token 的已完成子任务，父任务自身消耗 150 后成功，最终仍报告 150。该复现使用模拟消耗，没有真实付费调用。

建议：采用整个 run 共享的 BudgetLedger。为并发请求预留预算，响应后用 provider usage 结算；记录自身和子任务消耗，按唯一调用 ID 防止重复计算。正在执行的请求可能有超额，需要明确边界并设置输出上限。

验收：整次运行总量等于所有唯一模型请求的总和；通知重复投递、阻塞等待与失败子任务不会漏记或重复记账；预算停止规则可以独立测试。

### R07 · P1：GitHub Issue 自动提交混入用户已有的未提交修改

位置：[entry/github_issue.py](../entry/github_issue.py#L368)。

入口直接复用已有仓库，运行完成后执行 `git add -A`。没有在任务开始前建立与用户脏工作区分离的提交边界。

实际临时 Git 仓库复现：用户预先修改 `unrelated.txt`，模拟 Agent 仅修改 `fix.py`；使用 `create_pr=False` 执行完整入口后，生成的提交同时包含这两个文件。没有推送或创建远端 PR。

建议：GitHub Issue 任务使用独立、干净的 worktree/clone，从指定基线开始；仅提交该任务产物。若必须复用脏工作区，先明确拒绝自动提交，或建立精确的任务差异隔离，不能把 `git add -A` 当作任务归属判断。

验收：已暂存、未暂存与未跟踪的用户改动都保持原状，均不进入 Agent 的提交。

### R08 · P1：冻结的 30 题数据集指纹无法跨 Git 换行符转换使用

位置：[evaluation/suite.py](../evaluation/suite.py#L34)、[.gitattributes](../.gitattributes)。

manifest 对工作区 JSON 原始字节计算哈希。本机数据集含 4,201 个 CRLF；Git 保存的同一文件是 LF，内容语义相同但字节不同。

实际复现：把 `git show HEAD:swebench_lite.json` 和 `HEAD:evaluation/swebench30.json` 写入临时目录后加载，直接报 `Dataset fingerprint differs from the frozen manifest`。这模拟 Git 原始文件的干净检出；并非真正发起了远端 clone。

建议：定义并版本化数据集规范化方式，例如解析 JSON 后按固定规则序列化再计算内容哈希；也可固定 JSON 的 LF 规则，并从仓库标准字节重建冻结清单。必须保留任务内容变化检测，不能简单移除哈希校验。旧实验清单需要明确迁移规则。

验收：Windows、Linux 和 Git 原始文件加载相同任务集合；实际更改问题描述、base commit 或任务数据时仍然拒绝复用。

### R09 · P2：编辑符号链接会悄悄把链接变成普通文件

位置：[tools/file_ops.py](../tools/file_ops.py#L35)。

读取时跟随链接，但原子写入的 `os.replace` 替换的是链接本身。

实际 Docker 复现：`alias.py → file.py`，编辑 alias 返回成功；alias 不再是链接，内容变为新值，真实目标 `file.py` 仍是旧值。

建议：明确策略：默认拒绝编辑符号链接，或解析并校验目标仍位于授权工作区后编辑真实目标。不能静默改变文件类型。

验收：仓库内链接、指向仓库外的链接、失效链接都有确定行为，并验证目标内容及链接类型。

### R10 · P2：部分公开配置可以解析，却没有影响运行

位置：[config/schema.py](../config/schema.py#L78)、[entry/cli.py](../entry/cli.py#L119)、[tools/shell_tool.py](../tools/shell_tool.py#L156)。

录制 Runtime 复现：配置 Shell timeout=1、max_output_tokens=100，实际执行使用 timeout=30，4,000 字符输出完整返回。实例构造没有注入这些配置，执行器仍使用常量。

静态检索还显示 `max_view_lines` 和 `repo_map_budget` 在解析后没有连接到相应运行行为；history_window 则在 chat 中确有使用，不能笼统说所有配置失效。

建议：逐项建立配置到消费者的映射；定义 Token 与字符上限的单位。删除无效选项或接通实现，并提供脱敏的 effective config 显示。

验收：每个公开配置改变时，对应的外部行为确实变化；不同入口采用一致语义。

### R11 · P2：显式配置文件路径写错时，静默切换为默认模型

位置：[config/schema.py](../config/schema.py#L202)。

实际复现：显式传入不存在的配置路径，不报错，返回 provider=`anthropic`、model=`claude-sonnet-4-5`。这与“没有指定配置时寻找默认值”是两种情况。

若对应凭据存在，可能使用错误模型；没有凭据时通常会在后续报认证错误，掩盖真正原因。没有证据表明本次产生了错误计费。

建议：显式路径不存在、未知配置键和无效数值在预检阶段给出可定位的错误；只有未指定路径时才走默认查找策略。启动前显示脱敏的实际模型、接口、工作区、镜像和预算。

验收：不存在的显式路径在发出模型请求前失败，且错误指出该路径。

### R12 · P2：GitHub Token 被拼入 clone URL，容易进入仓库元数据

位置：[entry/github_issue.py](../entry/github_issue.py#L198)。

通过伪密钥和录制 `_run_git` 确认，clone URL 使用 `https://TOKEN@github.com/...`。Git clone 通常把 origin URL 保存到 `.git/config`，后续远端查看或诊断输出可能包含它。仓库会挂载到任务容器中，因此容器断网不等于凭据不在可读文件里。

本轮没有读取真实 Token，没有向 GitHub 发起该复现，也没有确认真实凭据已经泄漏。

建议：通过 credential helper 或一次性认证配置提供凭据，remote 保持无密钥 URL；日志统一脱敏。对历史 remote 做本地无输出扫描和脱敏迁移，避免把真实值打印出来。

验收：用伪密钥完成集成验证后，配置、remote、日志和导出产物均不含该值。

## 3. 项目如何进一步变好

以下是架构与能力改进建议，不能与上述已复现故障混为一谈。每项都应通过任务结果和消融实验确认收益。

### 3.1 保留主循环，增加少量明确的运行服务

当前各层抽象已经具备基础，不建议直接重写成复杂的多 Agent 框架。先围绕现有 Agent 注入以下服务，并提供默认实现，逐步迁移调用点：

| 服务 | 负责什么 | 解决当前什么问题 |
| --- | --- | --- |
| RunContext | run/task 身份、基线、权限、环境、取消信号 | 入口和子任务语义不一致 |
| ToolExecutor | 参数校验、权限、命令执行、超时与结构化结果 | 工具各自处理确认、转义、错误 |
| ArtifactStore | diff、测试输出、失败快照与内容哈希 | 失败清理丢成果、大补丁依赖模型转述 |
| BudgetLedger | 自身/子任务用量、请求预留、实际成本 | 多 Agent 漏计和并发超预算 |
| RepoIndex / ContextBuilder | 相关代码检索、增量索引、证据保留 | 静态地图与纯滑动窗口局限 |

Runtime 底层区分“执行参数数组”与“执行明确的 Shell 脚本”，同时支持 stdin；工具层不用感知宿主机命令行长度。先适配现有类，再拆分职责，避免一次性迁移所有模块。

### 3.2 用轻量阶段状态提高完成质量

保留 ReAct 的灵活探索，在外层维护少量可验证状态：

`理解问题 → 建立复现/基线 → 定位证据 → 最小修改 → 定向验证 → 差异审查 → 交付`

阶段不是强制每题走完的长计划。简单任务可以快速通过；复杂任务至少知道目前缺的是“没有复现”“还没定位”“验证环境失败”还是“补丁不正确”。

当前“连续若干步未编辑就反思”的策略应结合阶段判断。分析任务和复杂定位可能需要较长探索；只按无编辑次数催促修改，可能诱导过早打补丁。建议依据重复无新信息、相同错误与定位进展触发反思。

验收：统计过早编辑、重复失败编辑、无效探索与完成门禁拒绝的比例；在同一模型同一任务集上验证，不凭提示词看起来更合理就认定提升。

### 3.3 从全仓库静态摘要升级到任务相关上下文

现有 Repo-map 主要按顶层符号数与文件大小排序，不理解本次问题。缓存按仓库路径失效，同一仓库中新建/修改文件后仍可能继续显示旧摘要。

建议按成本从低到高推进：

1. 从报错栈、测试名、符号名和用户提及路径提取线索，优先使用现有文本/符号搜索。
2. 加入 import、引用与调用关系，把直接相关文件和一跳依赖优先注入。
3. 按文件内容哈希或版本增量更新索引，编辑后使受影响摘要失效。
4. 将已确认根因、相关路径、失败命令、当前补丁和下一步保存为任务状态摘要，防止滑动窗口只保留最近消息却遗失关键证据。
5. 统一加载适用的仓库约定，并明确用户指令、项目规则和待分析文件内容的优先关系。

先测“定位到正确文件需要多少步、检索结果有多少有效内容、每次请求输入成本”。没有证据需要语义检索前，不必增加向量数据库。

### 3.4 完整保留模型原生工具会话

目前工具动作被格式化为 assistant 文本，Observation 则作为 user 文本回传，工具调用 ID 与原生调用块没有完整贯穿主循环。它仍可能正常工作，本轮没有证明它单独导致模型失败。

建议扩展统一消息模型，保留 assistant tool_calls、tool_result、调用 ID，以及服务端要求回传的推理/签名块；各 provider 适配层负责转换。历史压缩必须按调用与结果成组处理。文本 fallback 保留为明确的兼容模式。

验收包括真实多轮工具调用的接口兼容、流式与非流式一致性、错误恢复；能力收益单独 A/B，不与其他大改一次性混测。

### 3.5 分开上下文窗口、累计消耗和金额预算

目前 `budget_tokens` 同时参与上下文分配和累计运行停止。这是不同的约束：单次请求能放多少内容、整次运行能花多少 Token、用户愿意花多少钱。

建议分别设置 `context_window_tokens`、`max_output_tokens`、`run_token_budget` 与可选 `max_cost`，考虑工具 schema 和 provider 开销。服务端返回真实 usage 时采用真实值，缺失时明确标记为估算；缓存 Token、推理 Token 和价格版本在可获得时单独记录，未知值不要伪装成精确成本。

质量指标同时看解决率、每个已解决任务的成本、耗时和尾部高消耗任务，不能只看总 Token 少了多少。

### 3.6 把“执行完成”“验证通过”“问题解决”分开呈现

当前需求是修改后必须尝试测试，测试失败仍可交付并记录，这一规则本身不算缺陷。可以在保留该默认行为的前提下，增加清晰的结果层次：

- 执行：是否正常完成、耗尽预算、被取消或遇到基础设施错误。
- 产物：是否生成有效补丁、改了什么、是否混入无关文件。
- 验证：是否尝试、是否通过、是否因环境阻塞、测试实际覆盖什么。
- 解决：基准由官方 harness 判断，实际项目由任务验收或人工确认。

验证最好保存修改前基线，再验证修改后结果；按任务选择复现脚本、定向测试、相关回归与轻量静态检查。严格模式可配置“关键测试必须通过”，不应突然把所有任务的默认规则改为全量测试全绿。

### 3.7 多 Agent 应按证据启用，交付结构化产物

先确保单 Agent 的定位、编辑、验证闭环稳定。只读探索与独立审查更容易获得并行收益；并行写任务需要清晰的文件边界和补丁整合规则。

建议子任务显式输入目标、相关路径、已有证据、验收方式、权限与预算。输出使用 ArtifactStore 中的产物引用：base commit、补丁哈希、修改文件、验证记录、风险和完成状态。

父任务可以审查并应用产物，避免把大补丁打印到上下文后再让模型重新复制；应用前检查基线和内容前置条件，冲突返回结构化错误。失败产物与成功产物使用相同交付格式。

比较“单 Agent”和“有明确分工的多 Agent”时，要看净解决率、总成本、冲突率与耗时，而不是子任务数量。

### 3.8 让事件日志支持失败归因与恢复

已有 JSONL 事件流值得保留。在此基础上增加稳定 schema 版本、run_id、parent_id、模型请求 ID、工具执行耗时、错误类别、产物 ID 与验证证据。

错误至少区分模型决策错误、工具调用/编辑错误、依赖环境错误、网络/API 错误、预算停止与评分错误。否则“任务没完成”无法指导下一轮改进。

恢复应先做到“保留补丁和足够状态供人工/新运行接续”，再考虑自动断点续跑。自动恢复前必须校验代码、环境和工作区基线；已有日志不代表可以安全重放所有有副作用的工具。

### 3.9 补充真实平台契约测试和可重复安装

现有 CI 已有 Ubuntu 测试与 Docker 构建，不需要从零重建。优先补以下覆盖：

| 运行方式 | 核心验证 |
| --- | --- |
| Windows 宿主机 + Linux Docker | 长 payload、中文/空格路径、超时、文件内容与 Git 参数 |
| Ubuntu 干净 checkout | LF 数据集加载、符号链接、权限、真实 Docker 工具 |
| wheel 安装到新虚拟环境 | CLI 入口、公开配置、包含的资源、无源码目录依赖 |
| 任务失败出口 | partial patch、日志引用、取消、预算、资源回收 |
| 主/子任务共同契约 | 权限收窄、Token 合计、补丁来源、消息重复投递 |

测试优先覆盖外部行为，避免大量只复述实现的 mock 断言。为项目依赖和镜像建立可追溯的版本基线，记录测试环境；按依赖变化触发兼容检查。

### 3.10 改善配置、诊断和日常使用

提供一个统一预检入口，例如 `agent doctor`：检查配置路径、实际模型、脱敏接口、Docker Linux 引擎、镜像、挂载、项目依赖、测试命令和工作区状态。预检避免默认发起付费请求，网络连通测试应明确区分。

现有 MiMo 配置窗口可以继续使用，增加“配置保存成功”和“模型接口验证成功”的独立反馈。启动时显示实际采用的配置来源，不显示密钥。

同步 README 与使用文档中的实际安装路径、默认模型、测试数量、工具清单和 Docker 行为。当前介绍中仍有旧测试数量和部分旧名称，容易让使用者与维护者形成错误预期。

## 4. 如何可信地比较 Flash 与 Pro

先修复 R08 并完成所有任务镜像/依赖预检，再发起完整 30 题付费比较。保持同一组任务、base commit、镜像身份、Agent 代码、工具、采样参数、预算和官方评分方式，继续采用交替模型执行顺序。

建议先用单 Agent 做主比较，避免把调度差异混入模型比较；再单独比较上下文策略或多 Agent 的收益。

每次报告至少包含：官方 resolved、基础设施错误、有效补丁率、目标测试通过情况、总 Token、可获得的金额成本、耗时分布，以及逐题成败交叉表。保留配对统计和置信区间；30 题差异较小时应报告不确定性。

这 30 题一旦反复用于调试，就应视作开发集。工程策略稳定后，再用未参与调试的保留任务验证泛化。单题 gold、接口小请求和微型任务继续作为联通测试，不能计入模型胜负。

建议按失败类别回答原先的模型问题：

- 如果正确工具调用仍执行失败，优先修工具与 Runtime。
- 如果相关文件没有进入上下文，优先修定位与检索。
- 如果相关证据齐全但补丁推理错误，再分析模型能力和提示策略。
- 如果基础设施正常、同条件下 Pro 有稳定优势，再考虑默认模型或任务路由。

## 5. 推荐实施顺序与验收门槛

| 阶段 | 内容 | 完成标准 |
| --- | --- | --- |
| 第一阶段：可靠执行与改动归属 | R01、R02、R03、R04、R07、R08 | 长内容不失败；参数不执行成命令；只读和确认生效；用户改动不混入；干净检出能加载评测 |
| 第二阶段：失败可恢复、成本可解释 | R05、R06、R09、R10、R11、R12 | 各种退出均保留产物；子任务不漏记；文件类型与配置行为明确；凭据不进入 remote |
| 第三阶段：提高任务成功率 | 阶段状态、相关检索、证据摘要、原生工具会话、验证分层 | 同模型同任务集做逐项消融，确认解决率或成本有实际收益 |
| 第四阶段：再扩展协作和策略 | 多 Agent 产物交付、模型选择、成本路由 | 以总成本下的解决率和耗时证明收益，失败可以定位和恢复 |

具体开发时，每项采用“最小复现 → 修复 → 对应回归 → 受影响集成验证 → dev 提交”。共享 Runtime 和权限接口的改动可集中设计，但应拆成可审查的小提交。全部验证前不合并 main。

不建议此时优先投入：重写整个框架、增加大量角色、引入向量数据库、增加复杂自主规划层或训练自有模型。应先让当前模型通过可靠工具获取相关证据、生成最小补丁，并留下可信的验证与成本记录。
